## Summary

GC-36 makes the app notice a dead Garmin key as soon as Garmin rejects it, instead of relying only on the expiry date typed on the You screen.

1. A 401 on the token exchange is classified as "key invalid" and stored on the sync run as `error_code = 'keyInvalid'`, so it is not an anonymous error string.
2. A 401 is never retried inside a pull. The run stops at once.
3. The Today and You screens show a banner ("Garmin rejected the key") with renewal steps. It clears itself after the next successful pull.
4. Scheduled pulls back off while the key is dead: 6 h, 12 h, then 24 h between probes. Manual Refresh and a server restart always probe, so fixing the key takes effect immediately.
5. The existing 409 `keyExpired` guard on `POST /api/sync` stays as a second guard.
6. Needs you: one DB migration (nullable `error_code` column on `sync_run`). The dead-key state is derived from run history, so no new settings key and no in-memory flag.

## Implementation

### Steps

1. Kanboard: `unipi-kanboard start GC-36` before editing.
2. `src/garmin/client.ts`: add `GarminKeyInvalidError extends GarminApiError`. `exchangeToken` throws it on a 401 only. Check 403 against a real response before including it (AGENTS.md rule). A 401 on a data call after a forced re-exchange stays a plain `GarminApiError`.
3. `src/sync/backoff.ts`: no behaviour change, since 4xx is already non-retryable. Add a test that pins it for `GarminKeyInvalidError`.
4. `src/db/schema.ts` and `drizzle/0003_*.sql`: add `SYNC_ERROR_CODES = ['keyInvalid']` and nullable `sync_run.error_code`. Generate with `npm run db:generate`.
5. `src/db/repos/sync-run.ts`: `finish(id, { error, errorCode })`. Add `trailingKeyInvalid()`, which returns the count of consecutive newest `keyInvalid` runs and the last `finishedAt`.
6. `src/sync/run.ts`: when a pull throws `GarminKeyInvalidError`, stop the run like the rate-limit break. Finish with `errorCode: 'keyInvalid'` and a fixed safe message. The `OutCome` type gains `errorCode`.
7. `src/sync/status.ts`: add `lastRun.errorCode` and `keyInvalid: boolean` (latest finished run is `keyInvalid`).
8. `src/sync/scheduler.ts`: new optional `shouldRun(now): Promise<boolean>`, checked only on slot fires, not on the startup catch-up. `src/sync/index.ts` wires it to the decay rule `min(6h * 2^(n-1), 24h)` after the last failure. Log a skip line.
9. `src/app/api/sync/route.ts`: no refusal on `keyInvalid` (manual refresh is the probe). Keep the 409 typed-date guard.
10. UI: `KeyBanner` takes `invalid: boolean` in addition to `expiry`. The expired-by-date banner wins, then the invalid banner (rose, renewal steps, "last rejected at …"). Wire it into `src/app/page.tsx`, add `keyInvalid` to `YouState` in `src/you/state.ts`, and show it on the You key row.
11. Docs: `docs/changes.md` entry (note the heading `GC-36` already names the coverage-floor work, so use a distinct title), a note in `docs/garmin-api.md`, and update the memory `garmin_key_expiry_runtime_401_not_api_expiry`.

### Risks

- Whether Garmin returns 401 (not 403) for a revoked key is unverified. Confirm with a real response or record it as an assumption in the docs.
- The migration must match `schema.ts`, or `db:check` fails.
- Existing rows have `error_code` null, which is fine.
- `knip` flags any new export that is unused.
- Decay state is derived from `sync_run`, so the repo query must stay cheap. It reads the newest few rows and stops at the first non-`keyInvalid` row.
- The error message stored on the run must never include the key or the response body.

### Verification

- Unit tests:
  - the exchange 401 throws `GarminKeyInvalidError`, and a 500 does not
  - a 401 is not retried (the fetch call count stays at 1)
  - the run stops and stores `errorCode`
  - the next success clears `keyInvalid`
  - the scheduler skips slot fires inside the decay window and probes after it
  - the catch-up and manual paths ignore the decay
  - the banner renders for invalid, expired and ok states
  - `POST /api/sync` still returns 409 for an expired date and accepts a manual refresh while `keyInvalid`
- `npm run verify` must pass in full, and the result is reported.
